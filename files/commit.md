# Commit Standards (Baseline Defaults)

These are baseline commit standards applied globally. They are a **floor**, not
a replacement for repository policy.

A repository may add requirements in its own guidance (such as `CONTRIBUTING.md`,
`AGENTS.md`, `.specify/memory/constitution.md`, or similar). Repository rules
take precedence only where they are **stricter** or explicitly waive a specific
rule below. A repository that is silent on a rule does not opt out of it.

When in doubt, satisfy both: the repository rules and this baseline.

## Commit Message Format

All commit messages MUST follow the **Conventional Commits** specification
(https://www.conventionalcommits.org/).

Format: `<type>[optional scope][!]: <description>`

Supported types:

- `build`: changes to the build system or external dependencies
- `chore`: maintenance that does not change source or tests
- `ci`: changes to CI configuration or scripts
- `docs`: documentation only
- `feat`: a new feature
- `fix`: a bug fix
- `perf`: a performance improvement
- `refactor`: a code change that neither fixes a bug nor adds a feature
- `revert`: reverts a previous commit
- `style`: formatting or whitespace only
- `test`: adding or correcting tests

A scope is optional and SHOULD be a short noun describing the affected area,
for example `feat(parser): ...`.

A breaking change MUST be marked with `!` before the colon and SHOULD include a
`BREAKING CHANGE:` footer describing the migration.

## Line Length

Commit subjects MUST NOT exceed **72 characters**, and SHOULD stay within
**50 characters** when possible. The body MUST wrap at **72 characters** per
line.

Do not rely on the terminal, editor, or Git host to wrap messages. Long
subjects are truncated in `git log --oneline`, dashboards, and generated
release notes.

Trailer lines and URLs are exempt from the body line-length limit. The subject
limit always applies.

## Required Trailers

### Signed-off-by

All commits MUST include a `Signed-off-by` trailer with the author's name and
email. This certifies the contributor's right to submit the code under the
project's license (Developer Certificate of Origin).

When creating commits, always use the `-s` flag: `git commit -s`

### Assisted-by

Commits that were authored or substantially assisted by an AI tool MUST include
an `Assisted-by` trailer identifying the tool and model used.

Format: `Assisted-by: <tool> (<model>)`

Example: `Assisted-by: OpenCode (claude-opus-4-6)`

Use your actual tool name and model identifier when creating commits.

## Exempt Messages

The following autogenerated or temporary messages are exempt from the format and
line-length rules:

- merge commits beginning with `Merge `
- autogenerated reverts beginning with `Revert "`
- interactive-rebase markers beginning with `fixup!`, `squash!`, or `amend!`

## Validation

When the Git role's commit hook is enabled, Git validates the message before
the commit is created. The same check can be run manually:

```bash
python3 ~/bin/commit_lint.py --file .git/COMMIT_EDITMSG
```

To check a commit message before committing, write it to a temporary file and
pass that file to the command. Use `git commit --no-verify` only when a human
explicitly asks for it; it bypasses an enforced policy.

## Example

```
feat: add user authentication endpoint

Implement JWT-based authentication with token refresh support.

Signed-off-by: Jane Doe <jane@example.com>
Assisted-by: OpenCode (claude-opus-4-6)
```
